# Виправлення восьми проблем повторного аудиту

Погоджено користувачем: виправити знайдене в чинній реалізації; психологію, практичну користь і конкретні кроки не скорочувати. Дані на телефоні не змінювалися, сервери/застосунок не перезапускалися, deploy не виконувався. `diary-front/eas.json` не редагувався в цьому етапі.

| Проблема | Поточне виправлення |
|---|---|
| Luna бачила лише останнє уточнення | `plannerRequestContext.ts`: оригінальний запис/чекін, початкова відповідь і датована історія саме цього джерела; для розмови — тільки її повідомлення. Цілі повідомлення обмежуються бюджетом, пропуск позначається явно. DTO приймає до 60000 символів, формування історії використовує 55000 плюс короткий службовий опис. |
| Уточнення губилося за загальною помилкою | Основний опис називає одне сповіщення завдання, кілька події, неперетин повторів і цілу кількість виконань. Luna повертає `plannerCreationQuestion`; він показується в службовому блоці й додається до наступного запиту. Для локальних помилок є локалізовані причини. |
| AI обходив обмеження форми | Спільний серверний/згенерований клієнтський контракт: опис завдання ≤2000, custom unit ≤30, count — ціле число. Перед записом перевіряються ті самі native `allowsDailyRecurrence`, `recurrenceOverlaps`, допустимі дати й сповіщення. |
| Часткове створення могло повторно трактувати команди | Журнал у наявній зашифрованій таблиці фіксує перший валідний набір команд. ID залежать від цього незмінного порядку. Збереження фіксується перед налаштуванням сповіщень. Явна кнопка повторює локальне виконання без Luna; ручні правки не перезаписуються, видалений частково збережений планер не відновлюється. Уже збережені назви видно при помилці. Після успіху копія команд очищається. |
| Підказка про місце ігнорувала глобальні фільтри | Використовуються справжня Today timeline, `isTodayCardVisible` і глобальні категорії календаря. Підказка враховує приховану картку, а не тільки `showInToday/showInCalendar` сутності. |
| Модель не бачила всього розкладу | `goalsContext.ts` передає всі інтервали виконання, режим тижня, завершення; live planning context читає збережені сповіщення звичок/цілей, завдань і подій. Норма залишається на весь день/тиждень. OS notification IDs не передаються. |
| Частина промптів перевищувала 3000 | Ущільнено тільки технічні правила можливостей, контексту, зображень і мови. Матриця розширена до 216 випадків. Максимум 2990 o200k токенів. Довільні особисті дані, історія, медіа, provider framing і Luna не входять у цей фіксований ліміт інструкцій. |
| Розмова і Luna мали різні цикли обліку | `timingTraceId` відповідає ID головного запиту. У новому протоколі успішна розмова/підсумок/діалог підсумку не закривають діагностичний цикл до Luna; незавершена відповідь закривається без виконання дій. Legacy і платіжні authorities збережені. |

## Зміни інструкцій

- Luna: попередня відповідь як єдине джерело уточнення → обмежена історія запиту з датами та фактичними результатами; історія ніколи не дає нового дозволу на виконання старих команд.
- `CLARIFICATION_REQUIRED` без пояснення → та сама ознака + одне конкретне питання мовою відповіді, без часткового набору дій.
- Загальне «alerts» → одне сповіщення завдання / кілька для події; неперетин повторів; цілі count-значення; явні ліміти тексту в повному контракті.
- Розгорнутий технічний опис можливостей/зображень/мови → коротші еквівалентні правила. Назви UI, області дії повторів, приватність спільноти, згода на створення, підтвердження пропозиції зображення та заборона редагування планерів збережені.
- Вісім захищених блоків психології/доказовості/користі/практичних кроків і задач відповідей перевірено SHA-256 проти погодженого baseline. Слова і абзаци цих блоків не змінені.

## Перевірка

- Бекенд: 307 різних тестів у 7 пов’язаних наборах — PASS після виправлення застарілих текстових очікувань. Додаткові gateway checks попереднього запуску — 32 PASS. Результати актуальних перевірок: `.tmp/planner-fix-tests3.json` + остаточний повтор трьох prompt-наборів `.tmp/planner-fix-prompt-final.json`.
- Фронтенд: 177 різних тестів у 11 наборах — PASS. Зокрема порядок/ідентичність команд, видалення між збереженням і повтором, прострочений час уже збереженого планера, уточнення, фільтри видимості, інтервали/сповіщення в контексті, структура діалогових повідомлень, відновлення початкового тексту підсумку після службового доповнення запиту, службовий блок і явний retry.
- Справжня SQLite в пам’яті: `node --experimental-sqlite scripts/test-planner-receipts.cjs` у фронтенді — PASS. Перевірено legacy migration, COALESCE незмінних команд, частковий результат, очищення після успіху, rollback при зміні власника. Мобільна БД не відкривалася.
- TypeScript обох проєктів, scoped frontend ESLint, parity згенерованого контракту й локалізованих 17 UI-назв, `git diff --check` — PASS.
- Заміри промптів офлайн: `node scripts/measure-planner-prompt.cjs`; 216 випадків, MAX 2990.

Старий широкий `memory-capsule-v2.spec.ts` із 7 раніше зафіксованими невідповідностями сторонніх тестів не оголошується зеленим; у цьому етапі він не запускався. Автоматичні тести використовують підставні відповіді провайдерів і не доводять живу якість моделі чи доставку сповіщень на телефоні.

## Наступна перевірка

Потрібні оновлений бекенд і новий фронтенд. Пройти вже погоджену регресійну мапу на збірці; не оголошувати локальні тести прийманням телефону. Додаткові знайдені ризики перевіряти лише в пов’язаному сценарії: кілька уточнень; одне завдання з надмірною кількістю сповіщень; повтор після часткового збереження; глобально прихована категорія. Зберегти фактичні input/cached/output/кредити головного виклику та Luna з одним trace ID.

Лічильник цього етапу: платні виклики AI — 0; кредити Nemory — 0. Токени Codex (fresh/cached/output) у доступних інструментах не надаються; оцінку замість фактичного обліку не підставляли.
