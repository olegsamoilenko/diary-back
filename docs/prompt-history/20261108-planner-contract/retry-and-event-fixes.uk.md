# Три виправлення після повторного аудиту — 8 листопада 2026

Дозвіл користувача: виправити три підтверджені проблеми та повторити сценарії. Психологію, практичну користь і конкретні кроки не змінювати; промпт не збільшувати.

## Реалізація

1. **Завершення події.** Канонічний v2-валідатор (і синхронізована копія фронту) відхиляє подію з часом початку та датою завершення без часу завершення. Немає вигаданої півночі або тривалості. Наявний механізм clarification обробляє відхилену команду. Виконавець не генерує timestamp завершення для відкритої часової події. Спільний сервіс створення/редагування додатково відхиляє закінчення раніше початку за локальними годинами або timestamps. Відкрите завершення, all-day і явно заданий перехід через північ зберігаються.
2. **Повтор аудіонотатки.** Чинна підготовка погодженого аудіо додає локальну ідентичність джерела. Журнал операцій в зашифрованій БД атомарно заморожує команди та `audio_sources_json`; нова nullable-колонка додається сумісно до старої таблиці. Це зв'язок дозволеного server ID з наявним локальним медіа, не копія аудіо і не нова таблиця. Абсолютні шляхи не зберігаються. Повтор читає джерело в поточному vault: для записів — чинний media row, для вкладень діалогу підсумку — погоджену приватну ідентичність файлу (вони не мають synthetic entry). Видалений/змінений journal media або зміна акаунта не допускають підстановки іншого файлу. Після успіху recovery metadata очищається. UI та протокол моделі не змінені; повтор не потребує нового AI-запиту.
3. **Дозвіл на сповіщення при повторі.** Preflight читає поточні налаштування збережених цілей, звичок, завдань, подій і нагадувань. Вимкнені сповіщення не викликають діалог дозволу. Увімкнені та нові сповіщення в змішаній операції його потребують. Повтор не повертає початкові параметри поверх ручного редагування; завдання синхронізує актуальні alerts, календарне нагадування використовує reconcile при повторі.

## Наступний круг: власний час, календарні дати, перша помилка OS і редагування серій

За дорученням користувача виправлено чотири знахідки нового аудиту. Перевірка цього круга автоматична; створення планерів на телефоні користувач виконає разом з асистентом пізніше.

1. Власна дата сповіщення завдання тепер задає зсув від кожного повтору. AI з конкретною датою та ручна форма з порожнім `customDayLocal` дають однакову серію. `utils/scheduling/notificationOccurrences.ts` спільний для перевірки форми та планування; виключення й завершення входжень збережені.
2. Місячні та річні події використовують конкретні дати з чинного календарного генератора: останній день місяця, 29 лютого та власне сповіщення напередодні узгоджені з календарем. Новий `utils/futureEvents/reminderOccurrences.ts` також використовується формою. Місячні/річні календарні нагадування використовують власний чинний `ScheduleRule`, без перенесення на них іншої семантики подій.
3. Ручна звичка зберігає початковий reminder через існуючий `createGoalWithMilestonesTx`, як AI-виконавець. Календарне нагадування зберігає primary alert в транзакції створення до OS-виклику; reconciliation відновлює і стару активну сутність без alert. Нових таблиць/полів немає. Відмова ОС більше не втрачає намір користувача.
4. Ручні форми завдання, нагадування й події перевіряють зміну розпочатої серії за майбутнім входженням, а не історичним початком. Нові та одноразові сутності зберігають захист від минулих дат. Завершена серія без майбутніх входжень не проходить зміну часу.

## Зсуви події, формат іконки та початкова дата нової звички
