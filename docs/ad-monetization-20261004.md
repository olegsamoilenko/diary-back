# Реклама і щомісячна підписка без реклами

## Поточний етап SDK — 4 жовтня 2026

За прямим запитом користувача підключено код AdMob Android/UMP у фронті; реальних показів ще немає. `GET /subscriptions/me` додатково повертає `advertisingRollout.enabled`, яке вмикається лише `ADVERTISING_ENABLED=true` у процесі сервера. Право `advertisingAccess` та AI/гаманці не змінені. Старі клієнти ігнорують нове поле. Фронт потребує свіжого права, дозволеного rollout і UMP canRequestAds, знімає покази при покупці та зміні акаунта. Поточні налаштування, тести й наступні кроки: `../diary-front/docs/advertising-integration-20261004.md`. Це уточнює старі записи про відсутній SDK нижче; sandbox-покупки/RTDN ще не прийняті.

## Карта реалізації

1. **Готово в коді: відокремити рекламний статус від AI-доступу.** Сервер обчислює його з чинного стану підписки; застосунок приймає через наявний запит підписки. Немає нових таблиць або збереженого дубліката права.
2. **Підготовлено в коді, прапорець покупки ввімкнений також для наступного production-випуску: підписка «Без реклами».** Каталоги legacy/V2, верифікація товару, RTDN, нуль включених кредитів, заміна покупки, чинні `Plans` / `PlansSettings` і uk/en/pl/de. Товар і базовий план створені в чернетці; потрібні активація для sandbox-покупок та перевірка ліцензійним тестером.
3. **Далі: інфраструктура реклами.** AdMob, UMP і параметри приватності, тестові ідентифікатори у розробці, можливість віддалено вимкнути рекламу. Потрібні реальні AdMob App ID / ad unit ID для випуску. Нова native-збірка для SDK. Перевірений актуальний статус підписки, згода і ввімкнений rollout мають передувати завантаженню реклами. Не передавати записи, чекіни, настрій, діалоги, пошукові запити чи інший приватний вміст рекламній мережі.
4. **Далі: одне місце показу та приймання.** Початкова пропозиція — нативна картка нижче основного вмісту списку «Сьогодні». Зберегти позначку реклами/AdChoices і вимоги SDK. Не переривати створення, перегляд, AI-діалог або пошук. Без порожнього слоту при помилці/no-fill. Перевірити теми, обидва розміри шрифту/line-height та справжній телефон. Місце й частота потребують конкретного перегляду перед ввімкненням.

## Реалізований контракт першого етапу

`GET /subscriptions/me` додатково повертає `advertisingAccess`:

```ts
{
  status: 'AD_FREE' | 'AD_SUPPORTED' | 'UNKNOWN';
  reason: 'PAID_SUBSCRIPTION' | 'TRIAL' | 'TESTING' |
          'NO_SUBSCRIPTION' | 'EXPIRED' | 'BILLING_INACTIVE' | 'UNVERIFIED';
  validUntil: string | null;
}
```

`AD_SUPPORTED` означає лише відсутність права на вимкнення реклами, а не дозвіл уже робити запит у рекламну мережу. `UNKNOWN`, відсутнє поле, неініціалізований акаунт — покази заборонені. Обробник реклами ще не реалізовано.

| Стан | Результат першого етапу |
| --- | --- |
| Lite/Base/Pro, оплачений період чинний | AD_FREE незалежно від залишку AI-кредитів |
| Скасоване поновлення, строк ще не минув | AD_FREE до expiryTime |
| IN_GRACE із чинним строком | AD_FREE за тим самим правилом, що й чинний paid-period access |
| Дата періоду магазинної підписки минула, але статус ACTIVE / IN_GRACE | UNKNOWN: не показувати рекламу до уточнення статусу магазину |
| Скасований оплачений період або ручний тариф завершився | AD_SUPPORTED |
| ON_HOLD / PAUSED / REFUNDED / EXPIRED | AD_SUPPORTED |
| Start протягом семи днів, зокрема після вичерпання кредитів | AD_FREE до expiryTime |
| Тестовий тариф | AD_FREE |
| Явний стан без тарифу | AD_SUPPORTED; куплені кредити не змінюють це право |
| Перехід «без AI» під час оплаченого періоду | Не забирає AD_FREE |
| Відсутній/невідомий/суперечливий стан або блокування акаунта | UNKNOWN |

Start і тестові акаунти поки виключені з реклами як консервативне правило початкового запуску. Чинне правило legacy-підписок без expiryTime збережене: допустимий billingStatus продовжує надавати доступ. Немає нової міграції, зміни коштів, списань чи AI-лімітів.

- `src/subscriptions/store-subscription-access.ts`: винесене без зміни поведінки правило оплаченого періоду. Використовується в існуючих перевірках доступу/власника покупки та новому розрахунку.

## Етап 2 — ідентифікатори та покупка

Для реалізації обрано:

| Рівень | Значення |
| --- | --- |
| Назва користувачу | Без реклами / Ad-free / Bez reklam / Werbefrei |
| Внутрішня назва в даних | `AdFree` |
| Код тарифу / base plan ID | `ad-free-m1` |
| Google Play subscription product ID | `nemory_ad_free` |
| Період / поновлення | 1 місяць / автоматично |
| Цільова базова ціна | USD 1.90; застосунок показує локалізовану ціну Google Play |
| Включені AI-кредити | 0 |

У Play Console створюється **окрема підписка поруч із `nemory`**, а всередині — базовий план `ad-free-m1`. Чинні `lite-m1` / `base-m1` / `pro-m1` залишаються всередині `nemory`. Це новий набір переваг; підписка в моделі Google описує переваги, базовий план — період/поновлення/ціну: https://support.google.com/googleplay/android-developer/answer/12154973?hl=en . Ідентифікатори — контракт підготовленого коду, не свідчення створення товару в консолі.

Вхідний товар перевіряється сервером за результатом Google API: `nemory_ad_free` допускає тільки `ad-free-m1` і навпаки. Не довіряємо product ID із клієнтського запиту. Новий тариф і в legacy mapper, і у V2 має `LIMITED / INSUFFICIENT_AI_CREDITS`; оплачений період водночас `AD_FREE`. Достатній баланс куплених кредитів дає AI через чинний wallet flow; тарифні AI-ліміти отримують звичний fallback Lite через відсутність активного AI-тарифу.

Чинний IapProvider обирає SKU за base plan. Між товарами передає попередній purchase token: у бік AI — `CHARGE_FULL_PRICE (5)`, щоб новий пакет AI-кредитів відповідав оплаті нового періоду; у бік «Без реклами» — `DEFERRED (6)`, після завершення вже оплаченого AI-періоду. Заміни між базовими планами всередині `nemory` не змінені. Користувач бачить умови оплати Google Play; для відкладеного переходу застосунок показує перекладене пояснення. Джерело режимів: https://developer.android.com/google/play/billing/subscriptions .

Google може повернути старий та майбутній line item разом. Верифікація вибирає item з найдальшим валідним expiry, а не перший елемент. Спільний `preservesDeferredCreditCycle` у subscribe і двох RTDN-гілках зберігає витрачені кредити того самого тарифу/періоду при переоформленні токена. Завершення старого нечинного токена не перезаписує актуальну іншу підписку. Потрібна перевірка справжніх sandbox-подій до активації продажу.

У фронті `EXPO_PUBLIC_AD_FREE_PURCHASES_ENABLED` без явного `true` приховує й блокує нову покупку. Після уточнення користувача `true` встановлений також для production, див. конфігурацію нижче. Вимкнений запуск не запитує новий каталог; після ввімкнення помилка нового SKU не прибирає поточні AI-тарифи. Відновлення/пошук наявної покупки враховують обидва товари; посилання керування підпискою використовує правильний SKU. Чинна UI-композиція й типографіка збережені, нові тексти через чотири каталоги перекладів. Візуальне приймання четвертого тарифу ще не проведене.

Наступний крок: активувати створений базовий план для sandbox-покупок, перевірити отриману з Play ціну й виконати сценарії нижче. Після цього підключати AdMob/UMP і рекламу. Прапорець production уже ввімкнений за прямим запитом користувача; реклама, виконані покупки й production-деплой цим не підтверджуються.

Користувач підтвердив збереження деталей після помилки форми і що Google-акаунт телефону є ліцензійним тестером. Ціна USD1.90, усі локалізації та активація не підтверджені скриншотом чи API. Не позначати їх перевіреними.

### Середовище

- `diary-front/.env.development`: локальний `EXPO_PUBLIC_AD_FREE_PURCHASES_ENABLED=true`. Файл ігнорується Git. Metro не перезапускали; застосування прапорця поточним bundle ще потрібно перевірити.
- `diary-front/eas.json`: окремий `billing-test` успадковує чинний `development` (internal dev client, локальний API), має власний channel і прапорець `true`. EAS `production` та локальний `.env.production` також задають `true` за наступним прямим запитом користувача. Звичайні EAS `development` і `browserstack` явно задають `false`. `billing-test` не підміняє API на production і не призначений для production OTA.
- Для поточного етапу нова native-збірка не потрібна, якщо використовується вже встановлений dev client з react-native-iap та package `com.soniac12.nemory`. Новий AdMob SDK згодом вимагатиме native-збірку. EAS build, публікація чи встановлення APK в цьому етапі не запускалися.
- ADB підтвердив підключений Samsung; порти Metro8081 і локального API3001 прослуховуються. Це не підтверджує отримання сервером RTDN. Перед перевіркою автоматичних поновлень встановити, куди налаштований Pub/Sub push, і що він обробляє ту саму БД/середовище, яке верифікує покупку. Не змінювати production Pub/Sub для локального тесту без окремої узгодженої схеми.
- Чинні живі шляхи: `PlansSettings -> Plans -> IapContext.buyPlan -> subscribeGooglePlayApi`; стартове відновлення `rootBootFlow -> restoreSubscriptions -> syncUser -> bootstrapSubscription`. Метод контексту `restore` оновлює каталог і використовується кнопкою повторного завантаження, а не окремою серверною кнопкою відновлення. Перевірка покупки вже є в `restoreExistingSubscription`.

### Порядок і докази

Для кожного випадку записати фактичний результат, час, тип доказу (Google checkout / серверна верифікація / RTDN / UI), без повних purchase token, даних акаунта чи вмісту щоденника. Усі наведені випадки поки **не виконані на телефоні**. Встановлення прапорця або успішний unit-тест не є прийманням покупки.

| ID | Перевірка | Очікування |
| --- | --- | --- |
| ADS-B01 | Каталог після активації | Ad-free поряд із чинними тарифами, локалізована ціна Play; інші тарифи не зникають |
| ADS-B02 | Нова покупка ліцензійним тестером | У checkout явно тестовий платіж; після підтвердження AdFree, AD_FREE, 0 включених AI-кредитів; wallet не змінений |
| ADS-B03 | Скасування діалогу / відхилення тестової оплати | Немає нового права, списання чи скидання кредитів; повторна спроба доступна |
| ADS-B04 | Повторне відкриття / відновлення чинної покупки | Сервер підтверджує те саме право, без нового списання та повторного пакета кредитів; не видаляти застосунок із локальними даними заради тесту |
| ADS-B05 | AdFree -> Lite (далі Base/Pro) | Негайна оплата AI-тарифу, один новий пакет кредитів, старе поновлення замінене; залишок вартості враховує Play |

| ADS-B09 | Grace / hold / відновлення оплати | Grace зберігає право, hold припиняє його, успішне відновлення повертає; без показу реальної реклами |
| ADS-B10 | Wallet із AdFree | AI лише за достатніх куплених кредитів; списання за чинним механізмом, відсутність реклами не залежить від балансу |

Для тестового checkout потрібен активний базовий план. Активація — налаштування каталогу Play, не спеціальний режим «лише тестери». Наступний production-випуск із новим прапорцем запитуватиме й показуватиме доступний новий товар. Саме ліцензійний акаунт і тестовий спосіб оплати забезпечують відсутність реального списання. Internal track сам по собі цього не забезпечує. Джерело: https://developer.android.com/google/play/billing/test .

Перевірка цього конфігураційного етапу: JSON EAS та assertions успадкування/каналу/прапорців успішні; `@expo/env.loadProjectEnv` окремо для development і production повернув `true`. Scoped diff-check без помилок whitespace. Платіжний runtime не змінювався, успішні попередні billing-тести повторно не запускалися. ADB прочитав поточну навігацію Nemory; вигляд нового тарифу й sandbox checkout ще не перевірені. Немає нових real/test purchases, публікації, перезапуску Metro чи підключеної реклами. Точні fresh/cached/output usage counters недоступні.

## Важливе для наступних етапів

- Нуль включених AI-кредитів явно оброблений у paid access і legacy mapper; збереження циклу при відкладеній зміні покрите тестами. Реальний sandbox checkout/RTDN ще потрібно перевірити.
- Після покупки, restore, зміни акаунта та повернення в застосунок необхідно отримувати актуальний статус до реклами. Під час покупки прибирати можливість показів. Кешований `AD_SUPPORTED` не може самостійно дозволяти рекламу після нової оплати; закінчення `validUntil` не повинно локально вмикати рекламу без оновлення сервера.
- Відповіді mutation API ще не містять нового поля; на першому етапі джерело — GET. Перед підключенням SDK завершити життєвий цикл актуальності, а не покладатися лише на необов'язковий тип у Redux.
- Store IDs, реальні платежі, Google Play upgrade/downgrade та AdMob/UMP ще не перевірені на телефоні. Зміна цього етапу не змінює видимий UI і не запускає рекламу.

## Перевірки

- Backend: 79 тестів у 4 цільових наборах; після фінального доповнення повторно пройшли 62 тести двох змінених наборів. Набори legacy mapper і effective AI access не змінювалися після успішного запуску.
- Frontend: 3 тести API + 4 чинні тести thunk підписки.
- TypeScript обох репозиторіїв, ESLint змінених TypeScript/JS-файлів, scoped `git diff --check` — успішно. Jest запускався поза sandbox після помилки доступу до його TEMP; обмеження виправлено стандартним дозволеним запуском.
- Візуальне приймання не заявляється: UI цього етапу не змінювався.

Етап 2: 92 backend-тести у шести цільових наборах і 70 frontend-тестів у чотирьох наборах пройшли; після останніх змін повторно перевірені саме змінені набори (SubscriptionsService 32, IapContext 25). TypeScript обох репозиторіїв, scoped ESLint та diff-check успішні; JSON і шість нових ключів перевірено в усіх чотирьох локалях. У тесті PlansSettings застарілі очікування прибраного білого тла/відсутнього заголовка приведено до чинного SettingsContainer; сам дизайн цього контейнера не змінювався. Жодних реальних покупок або активації товару не було; Android-перевірка нового варіанта та справжніх переходів залишається перед запуском.

Облік використання Codex: точні fresh input / cached input / output для цього етапу інструментами не надані; усі три значення недоступні. Оцінку вартості API та зміну загальної квоти не підміняємо вигаданими числами.
