# NA-01 / NA-02 / NA-09 — адміністративний доступ

Статус: локально реалізовано; 233 автоматичні тести PASS, TypeScript --noEmit, scoped ESLint і git diff --check PASS. Деплой виконує користувач.
Ручних сценаріїв до поточного телефонного чекліста не додаємо — рішення користувача 29.10.2026.

## Зміни

- Наявний `AuthGuard('admin-jwt')`: support get-messages/update-status; увесь user-monitoring, user-statistics, user-settings, token-statistics, plan-statistics, finance-statistics, forum-moderation; п'ять адміністративних читань diary-statistics. Разом 30 маршрутів, включно з раніше захищеним admin-revenue.
- Support create-message та чотири diary-statistics add-* зберігають користувацький JWT. Не змінено маршрути, DTO, параметри, статуси успішних відповідей або спосіб входу.
- Спільна явна проєкція профілю для моніторингу (список і відповідь додавання), платних профілів і активності: без password/hash, кодів підтвердження/відновлення, DEK, сесій, purchaseToken/linkedPurchaseToken та зворотних зв'язків із User. Платежі повертають явні фінансові поля, тарифи — поля відображення й кредитів. Розраховані лічильники та compact/legacy arrays збережені.
- Повні сутності в БД, авторизаційні запити та схему БД не змінено. Немає міграцій, нових таймаутів, опитування або нових обмежень інтервалу статистики. Додаткове ресурсне зауваження NA-09 щодо довгих інтервалів не включено в цю правку доступу; після закриття маршрутів воно стосується авторизованого адміністратора.

## Сумісність адмінки

- Live consumers: diary-landing/lib/api/{support,monitoring,usersStatistics,settingsStatistics,tokenStatistics,tokenUsageStatistics,financeStatistics,diaryStatistics,moderation}.ts; таблиці AllMonitoringUsersTable та UsersActivityTable; відповідні сторінки `/admin` і фінанси `/admin-v2`.
- Same-origin `/api` fetch надсилає cookie за замовчуванням; apiFetch використовує credentials=include. AdminAuthController встановлює admin_session з path=/; main.ts використовує cookieParser. AdminJwtStrategy перевіряє чинного адміністратора в БД, підтримує cookie та Bearer.
- Прибрано лише зайві дані відповідей, робочі колонки/фільтри/дії не перейменовано. Робочий код landing не змінено.

## Автоматичні перевірки

- src/users/admin-report-access.spec.ts: справжні HTTP controllers, ValidationPipe, cookieParser, обидві JWT strategies; анонімний/користувацький/прострочений/неактивний доступ, активні ADMIN/SUPER_ADMIN, cookie/Bearer, параметри й користувацькі маршрути. Сервіси замінено синтетичними, без БД і зовнішніх викликів.
- src/users/admin-report-projection.spec.ts: справжні сервіси з синтетичними query terminals; відсутність секретів у списках, додаванні моніторингу, compact/legacy/fallback активності та платних профілях; збереження лічильників, тарифів і paging.
- Існуючі user-activity-records.spec.ts та user-statistics.service.spec.ts: регресія статистики.
- diary-landing/tests/admin-report-compatibility.test.mjs: рендер справжніх компонентів таблиць із новою проєкцією (UI primitives/закриті дочірні діалоги замінено), виклик справжніх API wrappers із mock fetch; транспорт cookie, фільтри, delete, compact.

Це автоматичне підтвердження локального коду, не ручний PASS адмінки й не перевірка production reverse proxy. Приватні production-списки не запитувалися.

Результати: access+projection — 224 PASS; чинні два suites статистики — 6 PASS; landing compatibility — 3 PASS. Початкові запуски були заблоковані sandbox temp-cache/localhost та ESM-імпортом Expo SDK у Jest; кеш перенесено в .tmp, HTTP-тести запущено з дозволеним localhost поза sandbox, не задіяний SDK замінено mock. Три початкові assertions уточнено за реальною формою UserPlanState.name у синтетичному fixture. У фінальному запуску падінь немає.
