# NA-39 — готові embeddings при помилці історії

Статус: виправлено локально, автоматичні перевірки пройдено 29.10.2026. Ручне приймання відкладено до завершення всіх погоджених корекцій; деплой виконує користувач.

## Погоджена поведінка

Після успішного provider-виклику та списання кредитів помилка `addTokenUserHistory` не повинна відкидати готові вектори. `EmbeddingBatchService` окремо перехоплює цю помилку, реєструє її через чинний AiErrorReporter, продовжує запис у чинний Redis-кеш і повертає відповідь. Діагностика має чесно показувати незбережену історію.

Помилка самого `recordAiUsage` залишається помилкою запиту: не видаємо успіх і не кешуємо результат як оплачений. Ціна, округлення, пакетування, користувацькі ключі кешу та HTTP-контракт не змінюються. Глобальний `TokensService` та інші AI-потоки цією правкою не змінюються.

Компроміс: баланс уже врахований, але рядок історії токенів може бути відсутній. Автоматичне відновлення історії/нова черга не додаються. Повтор без provider/debit гарантується в межах чинного кешу за умови його доступності (типовий TTL 15 хвилин, чинний env може перевизначити). Якщо Redis також недоступний, поточний результат однаково повертається, але довготривалої дедуплікації повторів ця правка не обіцяє. Збій billing після платної роботи провайдера — окремий recovery-сценарій, не закритий перехопленням помилки історії.

## Автоматичні перевірки

**20 PASS / 3 suites:** `embedding-batch.service.spec.ts` (11, із них 5 нових), `tokens.service.spec.ts` та `ai-error-reporter.service.spec.ts`. TypeScript `--noEmit`, scoped ESLint і `git diff --check` — PASS. До зміни production-коду 4 нові сценарії відтворили втрату результату через history rejection; тест billing failure уже проходив. Provider, billing, Redis і транспорт повідомлень у цих тестах підмінені; це перевірка справжнього сервісного потоку, не production/Play/телефонне приймання.

- Помилка історії після списання: вектори й tokens повертаються, помилка реєструється, діагностика не стверджує `historyPersisted: true`; перевірка з trace та без trace.
- Повтор із новим requestId та новим екземпляром сервісу читає Redis без другого provider-виклику, списання або повторного запису історії.
- Одна помилка історії у спільному batch не впливає на іншого користувача; однакові тексти мають окремі кеші користувачів.
- Помилка billing: відмова, без запису історії/кешу та без успішної відповіді.
- Одночасна помилка історії та кешу: поточні оплачені вектори все одно повертаються.
- Чинні сценарії affordability, billing, розподілу provider tokens та старого texts/model контракту залишаються в тестах.

## Мінімальна ручна перевірка після всіх корекцій

**NA39.1 — DEFERRED / DEV із оновленим бекендом.** Включити в уже запланований основний сценарій запису/AI: зберегти запис із текстом, дочекатися індексації, підтвердити збережені embeddings і відсутність помилки в логах. Не створювати окремий додатковий AI-запит лише для цього тесту; використати результат спільного сценарію. Після деплою такий самий smoke можна зарахувати в основному PROD-сценарії, без дублювання.

Штучно ламати БД на телефонному/production тесті не потрібно: збій історії й відсутність повторного списання перевіряються автоматично. Успішне локальне збереження запису саме по собі не доводить успішної індексації.

Нові міграції, production env, frontend rebuild не потрібні. Реальні provider-виклики, production-дані, покупки й повідомлення під час автоматичних тестів не використовуються.
