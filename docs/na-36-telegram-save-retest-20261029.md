# NA-36 — Telegram не змінює результат збереження

Статус: локальна правка; деплой користувачем. Ручні перевірки DEFERRED до завершення всіх NA-корекцій. Наявні NA35/NA47 перевірки збережені.

## Реалізація

- Створення скарги, теми, коментаря (включно з коментарем через адмінку) надсилає Telegram тільки після успішного DB commit. При rollback/помилці commit повідомлення про створення не запускається.
- Редагування теми/коментаря також надсилає повідомлення після commit. Відповідь користувачу не чекає мережі Telegram. HTTP DTO та результат операції залишаються колишніми; допоміжні `{ value, telegram }` не виходять із сервісу.
- Чинні forum Telegram functions використовують один sender із catch навколо підготовки тексту й доставки. Повільна мережа, HTTP rejection, відсутність конфігурації чи помилка форматування не скасовують збереження й не породжують unhandled rejection. Навіть збій log sink не створює нове відхилення Promise.
- Для окремого фонового HTTP-запиту встановлено timeout 30 секунд, щоб мережеве з'єднання не залишалося відкритим безстроково. Це не час очікування збереження, модерації або інтерфейсу.
- Без автоматичних retry: загублена відповідь не доводить, що Telegram не прийняв повідомлення. Немає нової durable outbox чи гарантії доставки після перезапуску; невдала доставка логована, скарга/допис/лог рішення доступні в БД та адмінці.
- Лог містить лише канал FEED/MODERATION/REPORTS і фіксований опис; не містить Axios error, bot token, chat ID, текст допису чи скарги.
- Telegram-сповіщення про рішення модерації незалежне від публікації: BLOCK/ESCALATE_HUMAN і їхня чинна семантика не змінені. Збій Telegram не підмінює policy error і не зупиняє дозволене продовження. Форматування HTML збережено; поле userMessage тепер escaped.
- `community_changed` для створення тем/коментарів перенесено після commit; при невдалому commit сигнал не відправляється.

## Автотести

Результат: 79 унікальних тестів у 5 suites PASS (цільові запуски без подвійного підрахунку повторених suites); `tsc --noEmit`, scoped ESLint і `git diff --check` PASS. Початкові помилки типів у нових test fixtures виправлено, suite скарг повторно пройшла всі 5 тестів. Ручний статус нижче залишається DEFERRED.

- `forum-publication-consumers.spec.ts`: справжні service methods та Telegram helper, Axios/DB ізольовані; rejection, незавершений HTTP, commit ordering, rollback, адмін-коментар, moderation BLOCK/escalation. Збережені NA35 restrictions/own-delete та NA47 reservation regression checks.
- `forum-report-delivery.spec.ts`: успіх збереження при Telegram rejection/pending; duplicate report не створюється повтором; DB failure/commit failure не надсилають сповіщення; повтор після підтвердженої невдалої транзакції створює одну скаргу.
- `forum-delivery.spec.ts`: три канали, незмінний HTML, 30s лише для transport, приватність логів, formatter/config/logger errors; дочірній Node із `--unhandled-rejections=strict` та mock Axios залишається живим після rejected detached send.
- `forum-publication.spec.ts` і `send-telegram.spec.ts`: регресії lifecycle та незмінених plans/AI-error sender функцій.

Реальних Telegram/AI/push-повідомлень, публікацій або обмежень акаунтів у перевірках немає. DB commit змодельовано, production runtime не запускався й не зупинявся.

## NA36.1 — DEFERRED, об'єднати з основним сценарієм спільноти

Після backend deploy або на виправленому DEV бекенді створити й змінити тестову тему/коментар, надіслати одну скаргу. Після оновлення перевірити збережені дані й наявність скарги в адмінці; за налаштованого Telegram перевірити відповідні повідомлення. Окремий повтор цього сценарію після успішної перевірки не потрібен. Telegram outage/rollback/process-crash ручними діями не відтворювати: це покрито ізольованими автотестами.

## Деплой та межі

Лише бекенд, без нових env/залежностей/міграцій/frontend rebuild. Чинні TELEGRAM_FORUM_* налаштування збережені. Деплой виконує користувач.

Ця правка не додає DB-атомарність до статистики та push-доставки, що вже виконувались у транзакціях create. Їхні окремі збої все ще можуть впливати на операцію. Негарантована доставка Telegram після crash не приховується як успішна доставка; успішним є підтверджене збереження контенту.
