# NA-05 — токени, вхід та відновлення

Статус: локально реалізовано й перевірено. Деплой і ручні тести ще не виконані; деплой виконує користувач. Змін фронту, ENV або схеми БД для цієї правки немає.

## Що змінено

- `/auth/create-token` збережено як маршрут, але повертає 401 `SESSION_REQUIRED`: лише UUID/hash більше не видають токен. Навіть чинний bearer не перетворює цей маршрут на нескінченне продовження access-токена.
- Нові JWT: `id`, `uuid`, `credentialVersion`, стандартні `iat/exp`. Немає ORM-об’єкта, hash, password, кодів відновлення чи тарифів. Версія облікових даних — HMAC з серверним JWT-secret від наявного password hash та ідентифікаторів; нова колонка/міграція не потрібна.
- Перевірка HTTP та socket звіряє облікові дані з БД. Старі підписані JWT приймаються, доки їхній password hash відповідає поточному. Нові — за HMAC. Скидання пароля відкликає обидва формати без зміни глобального JWT-secret.
- Після правильного коду відновлення пароль і всі refresh-сесії змінюються в одній транзакції. Login/refresh/recovery/reset блокують рядок користувача перед рядками сесій, щоб одночасний запит не відновив відкликану сесію. Login перевіряє також, чи пароль не змінився після bcrypt-перевірки.
- `/sessions/recover-anon` використовує тільки ключ, раніше прив’язаний до цієї сесії. Переданий у запиті новий ключ не є доказом власності. Відновлення на наявному пристрої з його ключем зберігається.
- Уже підключений AI socket перевіряє токен перед новими діями. Запущена до reset операція не скасовується заднім числом; наявні broadcast-з’єднання не відключаються примусово, але нові підключення перевіряються.

## Межі сумісності

- Поточний фронт build 278 і попередній build 277 (`49e0975a`) використовують `/sessions/refresh` та `/sessions/recover-anon`; немає виклику `create-token`.
- Історія фронту: `3eb6d56b` від 2025-10-01 прибрав старий `utils/api/getToken.ts`. Не стверджуємо сумісність невідомих інсталяцій до цього переходу: продовження входу лише за UUID/hash закрито навмисно.
- Контракти login/email confirmation/Google/anonymous bootstrap, `user/plan/settings/aiPreferences`, refresh rotation та її grace-період збережені. Оновлення сервера саме по собі не відкликає чинні сесії.
- Якщо анонімна сесія або її раніше прив’язаний ключ уже втрачено, UUID/hash і довільний новий ключ більше не відновлюють доступ. Наявний opaque refresh для старих сесій без device key продовжує працювати. Дані/сесії на пристрої для тесту не стирати.
- Звичайне редагування пароля в налаштуваннях — окремий чинний шлях: старий access стає нечинним, refresh продовжує сесію. Повне відкликання всіх пристроїв тут стосується саме відновлення забутого пароля.

## Необхідні ручні тести

Усі DEFERRED UNTIL ALL CORRECTIONS за рішенням користувача 29.10.2026. Після завершення корекцій об’єднати з іншими необхідними сценаріями, розділити DEV/PROD і додати залишок production-перевірок; зберегти ID, уникати повторного проходження незміненої підтвердженої поведінки. Автоматичні тести не замінюють телефонне приймання та продовжують виконуватися під час виправлень.

- **NA05.1 — чинна встановлена збірка після деплою.** Не виходити й не очищувати дані. Відкрити застосунок: той самий акаунт, тариф/кредити й дані; відкрити спільноту та виконати звичайний короткий запит AI, якщо він доступний за тарифом. Не має бути примусового входу лише через деплой.
- **NA05.2 — відновлення email-акаунта.** На тестовому зареєстрованому акаунті пройти «Забув пароль» → код → новий пароль. Увійти новим паролем: той самий акаунт і дані. Старий пароль не входить. Якщо є другий пристрій з цим акаунтом, його стара сесія має попросити повторний вхід; другого пристрою спеціально не заводимо.
- **NA05.3 — інші способи входу.** Під час наступного звичайного тесту перевірити Google-вхід і продовження роботи на наявному анонімному профілі. Не видаляти профіль/сесію, не перевстановлювати застосунок для штучного сценарію втрати ключа. Перший запуск/пробний період також покриває автоматична регресія bootstrap.

## Автоматичні перевірки

Реальні JWT, bcrypt, Ed25519 і логіка сервісів на синтетичних репозиторіях: закриття uuid/hash входу, мінімальні claims, старий формат JWT, старий unsigned refresh, новий signed refresh/rotation, reset/OTP/rollback, конкурентні reset/refresh, запізнілий login, прив’язаний ключ гостя, блокування нового ключа, HTTP та socket revocation. Живі БД/Google/покупки не використовуються. Транзакційна модель тестів не є інтеграційним тестом PostgreSQL.

Результати 29.10:

- 512 HTTP-тестів PASS у шести suites: новий NA05 HTTP, profile update, settings update, admin reports, forum response security, notifications security. Старі fixtures доповнено відповідним користувачем БД, який тепер перевіряє JWT strategy; перевірки доступу не послаблені.
- 43 тести PASS: `auth.service`, `registration-ownership`, `session-security`. Остання suite включає 21 NA05 сценарій з реальними JWT/bcrypt/Ed25519.
- 8 тестів refresh rotation PASS; bootstrap/first-install atomicity, AI check-in gateway та conversation gateway також PASS.
- TypeScript, scoped ESLint і `git diff --check` PASS. Два наявні неформатовані gateway-test файли не форматували цілком: додано лише залежність конструктора.
- Ширший запуск `periodic-analysis.gateway.spec.ts`: два старі failures в очікуваннях аргументів `dialog` — implementation уже в HEAD передавав три додаткові boolean прапорці підтримки зображень, а expectations їх не містили. Тіло цих методів не змінювали; це не оголошено успішною регресією. Занотовано тут без нового ручного тесту чи змін логіки AI.

Перевірки не підтверджують production deployment, телефонне приймання або поведінку реального PostgreSQL під навантаженням. Для негайного відкликання access-токена перевірка HTTP тепер читає поточного користувача за primary key; фонового polling немає.

Облік використання: точні fresh/cached input та output tokens інструментами цієї сесії не надані; оцінку вартості не вигадували.
