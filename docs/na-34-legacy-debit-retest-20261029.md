# NA-34 — паралельні списання legacy-тарифу

Статус: виправлено локально; автоматичні перевірки пройдено. Деплой виконує користувач. Ручний сценарій відкладено до завершення всіх корекцій; телефонного/production приймання цієї правки ще немає.

## Зміна

- `PlansService.calculateCredits` блокує користувача, потім актуальний Plan у транзакції та читає лічильники після отримання блокування. Два списання більше не перезаписують результат одне одного.
- `SubscriptionUsageService.recordAiUsage` передає той самий EntityManager у списання та `syncLegacyPlanToUserPlanState`: Plan і його відображення у стані підписки фіксуються або відкочуються разом.
- Runtime перевіряється повторно під блокуванням. Якщо акаунт уже перейшов на V2, legacy-транзакція завершується і виконується штатне V2-списання.
- Legacy RTDN оновлює Plan у тому самому порядку блокувань User → Plan, щоб не утворити взаємне очікування зі списанням.
- Формули кредитів, кешовані/зображувальні токени, округлення, зовнішні контракти та гаманець куплених кредитів не змінені. Нових міграцій, production env чи фронтенд-білду не потрібно.

## Автоматична перевірка — 29.10.2026

**70 PASS / 4 suites:** 64 тести `plans.service.spec.ts`, `subscription-usage.service.spec.ts`, `subscription-legacy.mapper.spec.ts`; 6 тестів `legacy-debit-postgres.spec.ts` на справжньому PostgreSQL.

TypeScript `--noEmit`, scoped ESLint і `git diff --check` — PASS.

PG-сценарії використовують реальні сервіси й незалежні з'єднання:

1. Початкове використання 100, одночасні витрати 30 і 70: результат **200** в Plan і UserPlanState; до commit зовнішній читач бачить попередній узгоджений стан.
2. Помилка запису Plan: жодного часткового списання; наступна операція працює.
3. Помилка запису UserPlanState: Plan також відкочується; блокування звільняються.
4. Збережена формула для cached/cache-write/image токенів; після переходу на V2 використання списується штатним V2-шляхом.
5. Два прямі виклики calculateCredits також не гублять списання.
6. Одночасне legacy RTDN оновлення автопродовження та списання завершуються без deadlock і з узгодженими лічильниками.

Модульний тест окремо перевіряє зміну runtime між початковим читанням і отриманням блокування: V2-списання починається після завершення legacy-транзакції. Перевірені чинні помилки відсутнього плану й передача спільного EntityManager.

PG-тести створюють випадкову схему в локальній maintenance DB `postgres`, лише синтетичні дані, після запуску видаляють цю схему. `.env` застосунку та користувацька БД не використовуються. Початкову помилку метаданих тестової EntitySchema виправлено до успішного запуску; вона не була помилкою production-сервісу.

Повторити локально (не на production):

```powershell
$env:NA34_POSTGRES_CONTAINER='nemory-postgres'
node node_modules/jest/bin/jest.js src/subscriptions/legacy-debit-postgres.spec.ts --runInBand
```

## Необхідна ручна перевірка після всіх корекцій

**NA34.1 — DEFERRED / DEV із наявним LEGACY_COMPAT тестовим акаунтом.** Поєднати з основним сценарієм AI: виконати дві звичайні AI-дії, перевірити обидві відповіді та облік обох витрат у legacy Plan і стані підписки. Після повторного відкриття тарифу використання не повинно зменшитися. Runtime підтвердити на бекенді: стара версія застосунку сама собою не означає legacy-акаунт.

Не переводити реальний production-акаунт у legacy заради тесту. Якщо такого тестового акаунта немає, гонка вже покрита автоматично на PostgreSQL; не створювати зайву ручну процедуру, а звичайний V2 AI/billing smoke пройти у вже запланованому спільному чеклісті. Мілісекундну гонку вручну ловити не потрібно.

## Межі

Закрито відтворений lost-update двох legacy-списань та їх mirror. Окремий ризик старого Google snapshot у `IapService → PlansService → syncLegacyPlanToUserPlanState`, зазначений у NA-59, залишається відкритим: узгодження lock order не є повною перевіркою свіжості Google-відповіді. NA-20 (паралельний допуск за залишком) також окрема задача. Production, Play API, реальні покупки й дані користувачів цими тестами не змінювалися.
