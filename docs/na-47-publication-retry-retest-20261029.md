# NA-47 — повтор публікації після технічної помилки

Статус: локальна правка; деплой виконує користувач. Ручний ретест DEFERRED до завершення всіх NA-корекцій за рішенням користувача. Автотести не означають USER PASS.

## Поведінка

- Створення й редагування тем та коментарів використовують один lifecycle admission → moderation → DB commit → finalization.
- Redis атомарно резервує текст і місце у чинному вікні частоти. Паралельний дублікат не витрачає додатковий слот.
- Технічна помилка до запису або підтверджений rollback звільняє тільки власну reservation і повертає тільки власний слот у тому самому вікні частоти.
- Commit або BLOCK модерації зберігає антидубль. Помилка Telegram/читання після commit не відкриває повтор.
- Невизначений результат COMMIT, помилка rollback чи недоступність Redis при finalization не є доказом відсутності запису: блокування лишається до TTL. Це не повна ідемпотентність запиту після втрати відповіді/процесу.
- Поки спроба виконується, власний ключ поновлюється раз на хвилину; це не граничний час AI/публікації. Перед commit перевіряється власник. Redis ownership не замінює distributed transaction між Redis і PostgreSQL.
- Чинні ліміти 3 теми / 10 коментарів за 10 хвилин та помилки API збережені. Старі числові rate keys підтримуються без міграції.
- Побічні дії до commit (NA-36: push/Telegram/statistics) залишаються окремим пунктом; цей fix не робить їх транзакційними.

## Автоперевірки

29.10: 37 цільових тестів PASS (12 lifecycle + 16 live consumers + 9 real Redis); додаткова HTTP-регресія спільноти PASS (142 тести), 6 тестів нагадувань PASS. Повний `tsc --noEmit --incremental false` PASS після уточнення типу нижче. Реальних provider/Telegram/push викликів не було; PostgreSQL commit/rollback у цих тестах ізольовано mock-об'єктами.

`forum-publication.spec.ts`: rollback/commit, невизначений commit, помилка rollback, policy reject, ownership, heartbeat, cleanup errors.

`forum-publication-consumers.spec.ts`: чотири реальні service methods з ізольованими DB/provider/Telegram залежностями; технічна помилка, commit, rollback, post-commit failure, обидві гілки policy BLOCK.

`forum-publication-redis.spec.ts`: opt-in `NA47_REDIS_PORT=16379`; справжній локальний Redis в окремому тимчасовому контейнері, унікальний випадковий префікс, очищення лише ключів цього запуску. Конкурентні однакові запити, повернення слота, ліміти, новий власник/вікно, старий numeric counter. Після перевірок контейнер видаляється.

Додаткова HTTP-регресія: `forum-response-security.spec.ts` (доступ/проєкції API).

Підсумок: 185 тестів / 5 suites PASS (окремі цільові запуски), scoped ESLint і `git diff --check` PASS. Ручна перевірка та production deploy ще не виконані.

Під час фінального tsc виявлено TS2589 у `UserRemindersService.finishClaim`: широкий `Partial<UserReminder>` змушував TypeORM розгортати типи зв'язаних сутностей. Звужено тільки тип параметра до п'яти полів, які реально змінює завершення спроби (`status`, `sentAt`, `lockedAt`, `lastError`, `attempts`). SQL та поведінка нагадувань не змінені; перевіряється наявними тестами цього сервісу, новий ручний ретест не потрібен.

## Необхідний ручний сценарій

**NA47.1 — DEFERRED, DEV фронт + виправлений DEV бек.** Асистент готує контрольований одноразовий збій до збереження на ізольованому DEV стенді (без постійного debug endpoint/production fault flag). Надіслати звичайний дозволений коментар; після технічної помилки одразу повторити той самий текст. Очікується успіх без десятихвилинного блокування; після оновлення теми рівно один коментар. Не імітувати це вимкненням інтернету після Save: тоді результат commit невідомий і перевіряється інший сценарій.

Після деплою звичайне створення/редагування теми та коментаря включити в уже запланований сценарій спільноти, без окремого повторного великого циклу тестів. Паралельність і невизначені commit перевіряються автотестами, ручні кроки не додавати.

## Деплой

Тільки бекенд; нових залежностей, env, міграцій і frontend rebuild саме для NA-47 немає. Оновити всі backend-процеси: старий процес не вміє звільняти свою невдалу спробу. Старі duplicate keys природно завершують свій TTL; масове очищення Redis не потрібне.
