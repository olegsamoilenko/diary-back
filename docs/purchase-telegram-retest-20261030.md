# Telegram: підписки та купівля кредитів

30.10.2026. Погоджено повідомлення з ім’ям користувача, інформацією про пристрій і підписку/кредити. Уточнення користувача: поки окремий бот надсилає в його особистий чат; групу/канал можна підключити пізніше зміною chat ID. `getChat` підтвердив тип `private` і відповідність локально налаштованому ID; повідомлень ця перевірка не надсилала.

## Підключення

- Окремі `TELEGRAM_NEW_SUBSCRIPTIONS_BOT_TOKEN`, `TELEGRAM_NEW_SUBSCRIPTIONS_CHAT_ID` для обох типів покупок; немає fallback в alert/plans/forum чати. Для запуску доставки `TELEGRAM_NEW_SUBSCRIPTIONS_ENABLED=true`; без цього worker не читає чергу. Приклад без секретів: `.env.purchases-telegram.example`.
- Деплоїть користувач. Чинний `.github/workflows/deploy.yml` виконує build → migration:run → restart. Міграція `1793340000000-AddPurchaseNotifications` додає по два nullable-поля та частковий індекс до `payments` і `credit_purchases`. Нових таблиць, клієнтських контрактів чи залежностей немає; frontend rebuild не потрібен.

## Поведінка

- Нові рядки отримують `pending` у чинній транзакції покупки. Повторне підтвердження/RTDN/upsert не скидає маркер. Історичні рядки мають NULL та не розсилаються. Нові покупки, зареєстровані після встановлення цього коду при вимкненій доставці, залишаються в черзі до її ввімкнення.
- Worker раз на хвилину читає **локальну БД**, без нових запитів до Google. Підписки — лише `PROCESSED` після чинної фінансової синхронізації; кредити — після commit нарахування, `PURCHASED/CONSUMED`, ненульове нарахування без відкликаних кредитів. Новий оплачений період має окреме замовлення і повідомлення. Тестові покупки позначені.
- Статус `sending` і точний timestamp захищають від конкурентних обробників. До 20 рядків кожного типу за цикл; залишок продовжується наступним циклом. Транспорт Telegram до 30 с; помилка не змінює платіж/тариф/гаманець і не блокує відповідь покупки. Повтор або відновлення після падіння — через 5 хвилин.
- Строк доставки — наступний хвилинний цикл; для підписок може бути довше до фінансового підтвердження. Для кредитів невідома сума підписана «ще уточнюється», без вигадування ціни й нового повідомлення лише заради уточнення суми.
- Повторні перевірки покупки не створюють дубля. **Межа гарантії:** Telegram sendMessage не має ключа ідемпотентності. Якщо Telegram прийняв повідомлення, а відповідь загубилася або запис `sent` не зберігся, повтор доставки може створити дубль. Для звіряння є стабільний ID події. Exactly-once не заявляється.
- Повідомлення: ім’я/ID користувача, модель/ОС/версія та build застосунку, продукт/тариф або кількість кредитів, сума/валюта за наявності, order ID. Пристрій явно підписаний як **останні збережені дані акаунта**, не гарантовано телефон самої покупки. Немає email, purchase token, device unique ID, raw payload чи приватних записів; plain text, обмежені поля. Вхідні повідомлення бот не обробляє й не пересилає.

## Автоматична перевірка

Перший прохід: 65/65 PASS, 7 suites. Реальні SQL claims/міграція/upsert у випадковій ізольованій схемі PostgreSQL: два обробники, повтор після збою/падіння, історичні рядки, rollback, непідтверджені/повернені покупки. Unit transport/формат та чинні credit grant/terminal-state, payment finance і Telegram спільноти. Google/Telegram замінені моками; робочі дані не змінені, тестову схему видалено. TypeScript `tsc --noEmit --incremental false` PASS.

Для PG-тесту задати `PURCHASE_NOTIFICATIONS_POSTGRES_CONTAINER` на локальний контейнер і запустити Jest `src/payments/purchase-notifications-postgres.spec.ts` із workspace cache. Без змінної suite пропускається; це не SQL PASS.

## Необхідні ручні перевірки — PENDING

Проміжний реальний DEV-результат, 30.10: за прямим проханням користувача тестове повідомлення надіслано через backend `sendPurchasesTelegram`, API підтвердив успіх. Нова тестова купівля 20 000 кредитів залишилась `pending`, бо доставка ще була вимкнена під час уточнення адресата. У локальному ignored `.env` додано `TELEGRAM_NEW_SUBSCRIPTIONS_ENABLED=true`; одноразово виконано справжній `PurchaseNotificationsService.deliverPending`, результат `sent`, стан покупки `CONSUMED`, кількість 20 000 не змінена. Історична покупка з NULL-маркером не оброблялась. Це підтвердження транспорту й реального worker-а, **ще не підтвердження автоматичного cron у запущеному процесі чи USER PASS отримання**. Запущений бекенд має перечитати env при штатному перезапуску; асистент його не перезапускав. PROD/env не змінювались.

- **TG-PURCHASE.1:** після деплою та env оформити одну тестову підписку. Доступ активний; у погодженому особистому чаті повідомлення з користувачем, тарифом, замовленням, позначкою тестової покупки й останніми відомими даними пристрою. Повторити штатне відновлення/перевірку підписки: без нового повідомлення про те саме замовлення.
- **TG-PURCHASE.2:** одна тестова купівля кредитів. Нарахування рівно один раз; повідомлення з правильним пакетом/кількістю. Повторна перевірка тієї самої покупки не повторює повідомлення чи нарахування.

Поєднати з найближчими вже запланованими тестами оплат, не створювати додаткові покупки лише заради Telegram. Збій Telegram, два worker-и та rollback вручну не дублювати. Production deployment і автоматична доставка після нього ще не підтверджені.
